# Kotatsu Detailed MVP Plan
Problem: Build a self-hostable remote-machine manager with account registration, a web UI, a portable CLI, Linux daemons, machine inventory, and authenticated SSH-like interactive shell sessions relayed through the server.
Original starting point: an empty Git repository on `main` (before the Kotatsu rename). The implementation will use Go and target a Docker Compose server, daemon binaries for Linux amd64/arm64, and CLI binaries for Linux amd64/arm64, macOS arm64, and Windows amd64/arm64.
## Product behavior
* `kotatsu auth register` creates an account, assigns a stable user ID, and displays a newly issued account API token once. `kotatsu auth login` accepts an existing token and stores it in the user's config with owner-only permissions. The CLI supports server URL configuration and token revocation/rotation.
* `kotatsu ls` lists only machines owned by the authenticated account, including seven-digit machine ID, name, state, public IP, added time, and last-seen time. Online status is derived from agent heartbeat recency (initial policy: heartbeat every 30 seconds; offline after 90 seconds without a heartbeat).
* The web UI is plain HTML and JavaScript without CSS. It uses the same authenticated server APIs to show account-owned machines and enrollment-token controls.
* `/script/{auth-token}` serves an installer for Linux amd64/arm64. The installer downloads the matching agent release, checks its published SHA-256 checksum, installs the daemon and a systemd service, and enrolls the host. It reports progress and actionable errors. It must not silently install on unsupported systems.
* `kotatsu connect <machine-id>` opens a terminal PTY session to the selected machine. The user's terminal mode and dimensions are negotiated; exit restores the local terminal. The agent starts a local shell under its own restricted service account and returns terminal I/O through the relay.
## Architecture and repository shape
Use one Go module with separate `cmd/server`, `cmd/kotatsu`, and `cmd/agent` entry points, shared packages for versioned API types, authentication, configuration, persistence, and the PTY relay protocol. Keep the server, CLI, and daemon buildable as standalone binaries, without a bundled language runtime. Embed or serve the static UI from the server binary. Use SQLite with a persistent Docker volume for the initial deployment; keep database access behind a repository layer so a different database can be introduced later without changing API behavior.
* Server: HTTPS application/API, registration and token management, enrollment-script response, inventory, agent WebSocket endpoint, session authorization/routing, and static UI.
* CLI: account commands, machine listing, enrollment-token generation/revocation, and interactive PTY client. Store client config in the platform-appropriate user config directory with restrictive permissions where supported.
* Agent: Linux service that enrolls once, persists a per-machine credential, reconnects with backoff, sends heartbeats, and handles only server-authorized PTY session requests. It has no inbound listener.
* Installer: shell script returned by the script endpoint. It detects Linux architecture, fetches an immutable versioned release artifact, verifies its checksum, creates a dedicated unprivileged `kotatsu` account, installs a hardened systemd unit, and starts/enables the service. A machine uninstall procedure removes service files and local credentials.
## Authentication, enrollment, and session security
Keep account API tokens distinct from machine enrollment tokens and per-machine credentials. Generate cryptographically random opaque tokens, persist only secure hashes, show newly created tokens once, support revocation, and never return stored token material from APIs. Enforce account ownership on every machine and session operation.
* Enrollment tokens may be one-time or explicitly reusable, with expiration and revocation. Default to one-time and short-lived. The token in `/script/{auth-token}` is a bearer credential: require HTTPS outside development, rate-limit redemption, return `Cache-Control: no-store`, redact the path from application/proxy logs, and never use the account API token as the install token. Successful enrollment exchanges the enrollment token for a unique machine credential.
* Agent-to-server traffic is outbound TLS/WebSocket only. The server derives public IP from the observed connection address, honoring forwarded-IP headers only behind explicitly configured trusted proxies. The agent sends hostname and platform details, but these are display metadata, not authorization claims.
* A CLI session request is authorized against the account and target machine before a server-created relay associates the CLI socket with that agent. Only the CLI initiates a session. Do not include port forwarding, arbitrary network tunneling, server-side shell execution, agent-initiated sessions, or a publicly reachable listener in this MVP.
* Run the agent and spawned shell without root privileges. Do not retain terminal transcripts by default; retain only session metadata needed for troubleshooting/audit. Bound session duration/idle time and clean up child processes and relay state on disconnect.
* Use UUIDs internally and a collision-checked seven-digit numeric machine ID for display/input convenience. The short ID is not a credential; all requests still require account authorization.
## API and persistence outline
Define and version JSON endpoints for account registration, token exchange/revocation, machine listing, enrollment-token creation/revocation, machine enrollment, and agent heartbeat. Use authenticated WebSocket connections for agent control and CLI PTY sessions; the server performs authorization and byte-stream relay, not command interpretation. The initial tables/entities are accounts, account tokens, enrollment tokens, machines, and transient session records. Machine records include owner, internal UUID, display ID, name, public IP, created time, last-seen time, status inputs, and credential hash. Add database migrations and foreign-key/unique constraints for ownership and display IDs.
## Deployment and release workflow
Provide a Dockerfile and Docker Compose service for the server with a persistent data volume, configurable public base URL, and documented reverse-proxy TLS termination. Include health checks, graceful shutdown, and configuration via environment variables; never bake production secrets into the image. Provide local development instructions that clearly distinguish development HTTP from production HTTPS.
* GitHub Actions tests and builds on pushes/PRs; tagged releases build and publish checksummed archives for the CLI targets (Linux amd64/arm64, macOS arm64, Windows amd64/arm64) and agent targets (Linux amd64/arm64), plus version metadata and installer-compatible download names.
* Release artifacts should be reproducible from a version tag and include checksums. The installer must pin to a version or a server-selected stable version rather than relying on an unverified mutable binary URL.
## Implementation sequence
1. Establish module, package boundaries, configuration, structured logging, versioning, and basic build/test automation.
2. Implement database schema/migrations, registration/login, account token lifecycle, and authorization middleware.
3. Implement enrollment-token lifecycle, installer endpoint, Linux agent enrollment, heartbeat, and owner-scoped machine listing.
4. Implement CLI auth/list commands and the plain HTML/JS inventory and enrollment UI.
5. Implement outbound agent transport, server-authorized PTY session setup, local terminal handling, resize/exit/disconnect behavior, and the `connect` command.
6. Add Docker Compose deployment, installer hardening/uninstall, GitHub Actions cross-build/release workflows, and operational documentation.
7. Run unit, API integration, Linux service-install, PTY end-to-end, security, and cross-compilation checks; resolve failures before calling the MVP complete.
## Acceptance and validation
The MVP is complete when two accounts cannot see or access each other's machines; revoked/expired enrollment tokens cannot enroll hosts; an enrolled Linux host survives service restart and reports accurate online/last-seen state; `ls` and the web UI show the same owner-scoped inventory fields; and `connect` provides an interactive PTY with terminal resizing, clean exit, and no exposed inbound machine port. Tests cover token hashing/revocation, authorization boundaries, ID collision handling, heartbeat expiry, reconnect behavior, PTY lifecycle, installer architecture selection/checksum failure, and graceful server shutdown. CI must successfully build and package every requested target. Validate through private/test machines before public deployment; production must use HTTPS and trusted release artifacts.
